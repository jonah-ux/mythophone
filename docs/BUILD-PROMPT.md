# Build Mythophone: invent an instrument and actually play it

## Your mission

Build and publish an independently usable open-source project provisionally named **Mythophone**, targeting `jonah-ux/mythophone`. Deliver a browser instrument designer: describe an imaginary sound, let AI propose an editable synthesis patch, play it immediately, refine it while performing, and save/share the resulting instrument.

The desired reaction is: “I asked for a cello made of rain, and now I'm playing my own interpretation of that instrument.” Own the usable product, audio engine, real AI integration, verification, documentation, and public repository. A generated MP3, mock keyboard, landing page, or chat interface is insufficient.

## Context, ownership, and scope

- Jonah wants ambitious, fun public projects with a clear original contribution. An ordinary computer/browser and its audio output must be enough. Keyboard and pointer are primary controls; no MIDI controller, microphone, special board, paid DAW, or new hardware is required.
- Check the target repository and existing ownership/instructions before editing. Preserve other people's work and use a suitable isolated checkout. If the name belongs to an unrelated project, choose an available name without replacing it.
- If absent, create the standalone project and publish reviewed contents to a new public repository in Jonah's account through the available authorized GitHub route. Follow required merge/release owners; do not bypass gates or replace published history.
- Keep the product independent of private Fleet, Portal, Atlas, and Forgeyard runtime services. Reuse compatible public libraries with attribution; development helpers must not become hidden runtime requirements.
- Make routine choices yourself. Keep changes reviewable, Conventional Commits truthful, and any delegation bounded with explicit ownership. Ask only for information or authority that blocks a concrete step, and finish independent work meanwhile.

## The first performance

Support these illustrative prompts as expressive directions within a declared synthesis design space:

1. **“A cello made of rain.”** A sustained, expressive tone with a controllable airy/noisy texture.
2. **“A bell that crumbles into sand.”** A struck tone whose tonal decay gives way to a granular-looking/noisy texture produced by the supported engine.
3. **“A tiny mechanical dragon.”** A playful buzzing/growling patch with pitch, articulation, and a useful performance macro.

These are artistic interpretations, not claims of physically recreating those imaginary objects. Demonstrate alternate phrasings and edits such as “softer attack,” “less metallic,” and “keep the texture but make the decay longer.”

The interaction loop is **describe → inspect interpretation → play → tweak → save → perform again**. New requests should produce actual parameter/graph changes. A revision must preserve parameters outside its declared scope or explain the changes before applying them. A patch can be reverted.

Provide an on-screen keyboard, computer-keyboard mapping, a few meaningful macros, attack/release behavior, sustain, a master level, and a reliable all-notes-off action. Audio starts after an explicit user gesture. Losing focus, changing a patch, or navigating away must not leave stuck voices.

Ship a labeled no-key mode with three excellent prepared instruments. Live-AI generation is a distinct configured mode. Prepared patches must not be represented as freshly generated by a model.

## Original contribution and visual direction

Investigate related synths, text-to-preset tools, neural audio work, and sound-design interfaces briefly. Document the nearest relationships and compatible licenses. Pursue this contribution: **natural-language instrument design that produces portable, inspectable, editable patches and preserves expressive playability**.

Make the instrument enjoyable to perform. Give it a visual identity that responds to measured notes/envelopes/macros, a readable keyboard, and carefully chosen controls. Prefer a small number of well-mapped controls to an overwhelming parameter grid. Include an optional patch/signal-path inspector for people who want depth.

Use accessible contrast/focus states and clear keyboard instructions. Provide a reduced-motion presentation option. Keep provider internals and developer diagnostics out of the main performance flow. Make changes audible and controllable; visual effects must not substitute for sound generation.

## Engineering model

Prefer a small TypeScript browser application, a Web Audio engine, and a thin server-side model adapter. React/Vite and standard AudioNodes are reasonable defaults. Use a mature compatible audio library if it materially simplifies the engine; inspect current APIs and lock dependencies. No new model training is required for the first release.

Define a versioned **Patch** schema with a bounded supported design space. Start with a limited vocabulary such as oscillator/noise sources, envelopes, filters, simple modulation, a bounded delay/effect stage, mix levels, macros, and voice configuration. A small well-tested graph is better than an unbounded modular system.

Separate:

- **Patch schema/compiler:** validates the complete patch and builds a supported audio graph.
- **Performance engine:** schedules note events, voice envelopes, sustain, macro changes, voice stealing, and disposal.
- **AI sound designer:** maps a description or edit plus the current patch into validated patch data and a concise explanation of the interpretation.
- **Instrument UI:** provides actual notes/macros and visualizes measured engine activity.
- **Patch/performance storage:** versioned export/import, seeded noise where needed, note-event recording, and offline rendering.

AI returns data, never executable DSP, arbitrary JavaScript, AudioWorklet source, remote imports, or shell/tool actions. Validate versions, node types, graph references, finite numbers, parameter ranges, polyphony, effects, and resource limits before compilation. Reject broken/unsupported graphs atomically. On provider or compiler failure, keep the currently playable instrument.

Use documented server-side provider configuration. Secrets must never enter the browser bundle, exported patch, recording, sample assets, screenshots, or committed logs. Bound generation size, timeout, retries, and history. Cancellation should keep the player's current patch and performance state understandable.

Use the audio clock for scheduling. Define note-on/note-off semantics, voice limits, sustain release, macro mapping, and smooth parameter changes. Handle rapid edits, overlapping notes, reset, blur, and repeated initialization. Bound output gain and feedback as normal audio-engine quality requirements. Clean up nodes, timers, and event listeners.

Patch edits should occur at an explicit boundary and avoid accidental clicks or sudden discontinuities where practical. Document any first-release limit, such as edits applying to new voices while existing voices finish. Preserve a patch history entry only after successful compilation.

Offline rendering should exercise the same patch compiler/performance semantics as live playback. Keep a compact performance event format with timing, note, velocity, release, sustain, and macro changes. Export/import must actually recreate the instrument and a supported performance; it must not depend on another model request or an unavailable external sample URL.

## Build sequence

1. **Playable audio engine.** Build and tune three prepared patches with actual note generation, macros, sustain, cleanup, and an on-screen keyboard. Establish audible product quality before wiring AI.
2. **Real sound-designer adapter.** Connect one provider that returns validated patches and constrained edits. Verify alternate descriptions, revisions, refusal, timeout, and cancellation while preserving the active instrument.
3. **Portable instrument.** Add patch history/revert, versioned save/export/import, note-event recording, and a short WAV export through the same engine's offline rendering path.
4. **Release-quality performance.** Finish visual feedback, keyboard/accessibility behavior, demo recordings and downloadable audio, tests, fresh-clone setup proof, and public repository delivery.

Defer arbitrary DSP/code generation, training realistic instrument models, plugin distribution, marketplace/accounts, microphone analysis, gesture capture, and multiplayer. Those can follow a demonstrably good keyboard/pointer instrument.

## Acceptance criteria

Produce rerunnable evidence for the following:

- Actual note-on/note-off operations render finite audio with measurable signal energy. Different pitches and relevant patch parameters produce the expected supported changes; the tests must inspect rendered audio or engine state rather than only labels.
- Release, sustain-off, reset, focus loss, and navigation dispose or finish voices according to the documented envelope/tail policy. Assert bounded voices and no stuck-note accumulation through repeated play/edit/reset cycles.
- Prepared instruments are audibly distinct. Include original short rendered examples and listen when the environment permits. If only waveform/spectral measurements were available, report that precisely rather than claiming listening occurred.
- Use OfflineAudioContext or an equivalent real browser rendering path to measure representative attack/release, frequency behavior, non-finite output, peak bounds, and the silence/tail condition after the defined end of a performance. Document thresholds and why they test meaningful behavior.
- Invalid references, unsupported node types, extreme/non-finite values, excess resources, and incompatible versions are refused before a graph replaces the active instrument.
- At least one configured real provider completes description → validated patch → actual played/rendered notes. Test one scoped edit against the previous patch and verify the claimed parameter changes. Prepared responses and mocked-provider tests are separate evidence.
- Export a generated patch, reset/reload, import it, and play it again without another model call. Restore a recorded performance and export a WAV that a normal audio player can open.
- Browser verification uses the real keyboard/macros and visible measured activity. Exercise both no-key and configured-AI modes, including a failed request while the instrument remains usable.
- Measure interaction/audio resource behavior on the named test environment. Do not promise zero latency, all-browser support, or commercial instrument quality without supporting evidence.

Tests should defend the schema, graph compiler, musical event semantics, resource cleanup, and complete browser flow. A mocked AudioContext alone is not sufficient audio proof. If authorized model credentials are absent, finish the playable prepared instruments and identify exactly the missing live-provider proof rather than declaring the whole AI workflow complete.

## References to inspect, not runtime requirements

- [Web Audio timing](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/currentTime) explains the context clock; multi-device synchronization is outside this release.
- [OfflineAudioContext](https://developer.mozilla.org/en-US/docs/Web/API/OfflineAudioContext) renders a real audio graph to a buffer, which supports audio-level tests and WAV export without relying on a speaker recording.
- [Magenta DDSP-VST](https://magenta.tensorflow.org/ddsp-vst) is related neural synthesis work. Credit the relationship if used; first-release Mythophone can use AI-designed patches in an established synthesis engine.
